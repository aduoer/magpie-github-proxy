GitHub 代理

让 magpie 里的应用更新、插件、MCP、Skill 下载都走你配置的代理或镜像站。改的都是 magpie 自己的配置文件，不用重新打包 magpie。

·现在生效 实时

读的是 magpie 此刻真正在用的配置：每 8 秒自动重读，改完不用手动刷新这一页。

1代理通道 推荐

写进 magpie 的 settings.proxy。magpie 自己的所有 HTTP 都经过 netproxy： 检查更新、下载更新包、插件市场、插件安装（含 bun / npm）、Skill、MCP、插件的子进程，全都走它。 立即生效，不用重启。

SOCKS5 也能填：magpie 会给 Bun 的请求自动搭一条 http 桥，git 自己就认 socks5://。

2前缀通道 镜像站

代理和镜像可以同时设，也可以只设一个。它们是两条独立的路：代理是「把连接交给代理服务器」（第 1 节）， 镜像是「把 GitHub 原地址拼在前缀后面」（https://gh-proxy.com/https://api.github.com/…）。 只设镜像也覆盖得到 GitHub 相关的东西：更新与更新包走 updateMirror； 市场、插件安装、Skill、MCP 走 github.com、api.github.com、raw.githubusercontent.com、 codeload.github.com 这四个域名的前缀改写（magpie 的 source.URLs() 只给这四个加前缀）。 代理另外还能盖住前缀盖不到的：release 资产域（objects.githubusercontent.com）、镜像慢或挂掉时的大包、git 克隆。 


  


  

    
3Git 通道 代理通道的补丁

    

      magpie 装 git 型 Skill 时直接调 git，它的 gitEnv() 只加了几个变量，
      不注入代理环境，所以 git 不会走第 1 节的代理。这里改 git 自己的全局配置，只给 GitHub 的几个域名加
      http.<url>.proxy，别的 remote 一概不碰。
    

    

    

      
      
      
    

  


  

    
4自检

    
对 magpie 真正会用到的地址各探一次（HEAD，不下载内容）。直连一列红了、经代理一列绿了，就说明代理真的起作用。

    

      
      
    

    


    
前缀自检：把每个地址拼在现在的前缀后面各取一次响应头（不下载内容）。哪一行红，就是这条路的镜像不通、magpie 到时候会退回直连。

    

      
      
    

    

    
这一列没有 objects.githubusercontent.com（release 资产域）：它只给带签名的临时地址（?X-Amz-Signature=…），
      根路径什么都没有，探了也只能看到一个 404。而且走前缀下载更新包时，是前缀自己去取资产再流回来，根本不经过这个域名 ——
      它只影响「代理能不能连上」，所以在上面「全部自检」里看。
